# Formal Regression Manifests — T13–T18

> Status: Fixture design frozen for validation; T14 is the revision-1 replacement task.

These tasks describe behavior that the frozen source already substantially preserves. Formal benchmark instances therefore require controlled regressions rather than using the clean base directly.

---

## T13 — Visibility wake re-arms an exhausted stopped transport once

### Frozen behavior

A disconnected `WebSocketService` remains explicitly connectable even when its automatic reconnect counter is at the budget. A failed explicit attempt does not create an unbounded new automatic budget.

### Controlled fixture

Add an incorrect wake-path guard that treats a nonzero/exhausted reconnect-attempt count as terminal and skips the explicit visibility reconnect.

The fixture must not alter normal automatic reconnect behavior.

### Acceptance

Given a previously authenticated, live, non-disposed service in `disconnected` with an exhausted automatic budget:

- one visibility wake calls `connect()` exactly once;
- the explicit attempt does not reset the automatic budget merely because it started;
- subsequent failure does not create an unbounded retry loop.

Primary scope: visibility-wake + transport-reconnect.

## T14 — Preserve live transport across non-routing context churn

### Frozen behavior

`SessionRuntime.syncAgentConnection` keeps the existing WebSocket when effective URL/token are unchanged.

### Controlled fixture

Remove/bypass the same-endpoint reuse path so an ordinary context update rebuilds the `WebSocketService` even though transport identity did not change.

### Acceptance

After the initial transport is created:

- viewport-size update does not create another physical socket;
- transport-ready update does not create another physical socket;
- value-equivalent context update does not create another physical socket;
- an already accumulated transport reconnect-attempt count is not reset by those updates;
- an actual route-intent replacement may still rebuild as designed.

Primary scope: route-recovery + transport-reconnect.

## T15 — Same-URL route-intent change creates exactly one replacement transport

### Frozen behavior

The runtime uses a forced reconnect on route-intent changes, even when the resolved URL is unchanged. An existing visible test already proves exactly one new socket.

### Controlled fixture

Remove `forceReconnect` from the route-intent-change rebuild path. Same-URL intent change then incorrectly reuses the old transport.

### Acceptance

One route-intent epoch change resolving to the same URL creates exactly one new physical WebSocket, no zero-rebuild and no double-rebuild.

Primary scope: route-recovery + transport-reconnect.

## T16 — Preserve latest viewport size across reconnect

### Frozen behavior

The runtime stores the latest viewport independently of current transport connectivity and passes it into later attach attempts.

### Controlled fixture

Make a viewport update that occurs while the transport is disconnected/reconnecting fail to update the canonical `lastResize` used by the next attach.

One acceptable fixture is to gate viewport-state update on current connection readiness.

### Acceptance

Sequence:

```text
attach with 80x24
transport becomes unavailable
viewport changes to 120x40 while unavailable
transport recovers
new client.attach
```

The new attach must carry `120x40`, never the stale `80x24`.

Primary scope: route-recovery + reattach.

## T17 — Manual-route exhaustion never silently forces relay

### Frozen behavior

Manual transport exhaustion transitions attach state to `failed`; runtime emits transport exhaustion and remains under manual intent.

### Controlled fixture

Change manual `TRANSPORT_EXHAUSTED` handling to take the automatic fallback path (force relay / connecting) instead of failing.

### Acceptance

After manual-route recovery exhaustion:

- phase is `failed`;
- no `force-relay` runtime event;
- no relay begin;
- manual route intent remains authoritative until explicitly changed.

Primary scope: attach-state + route-recovery.

---

## T18 — Automatic recovery exhaustion forces relay exactly once

### Frozen behavior

`applyForceRelay` is idempotent once runtime config is already forced to relay, and current tests verify a single force-relay event for normal candidate exhaustion.

### Controlled fixture

Remove/bypass the idempotence guard so repeated or late recovery signals can execute force-relay transition logic more than once.

### Acceptance

For one automatic recovery exhaustion episode, including a repeated/stale recovery signal:

- exactly one `force-relay` runtime event;
- exactly one relay begin for the transition;
- P2P client remains torn down;
- later stale recovery cannot return the runtime to P2P.

Primary scope: route-recovery + attach-state.
