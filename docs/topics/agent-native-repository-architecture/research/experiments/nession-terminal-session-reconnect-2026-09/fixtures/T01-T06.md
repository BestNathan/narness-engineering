# Formal Fixture Manifests — T01–T06

> Status: Drafted after Pilot 0.
>
> These fixtures turn the first six task intents into controlled benchmark instances.
>
> A fixture is treatment input, not the expected solution. The agent must not receive this file.

## Shared rules

For every treatment:

```text
treatment base
  ↓
apply task fixture
  ↓
prove acceptance condition currently fails
  ↓
start fresh agent session
```

A/B use equivalent physical mutations because B keeps implementation topology materially unchanged.

C must reproduce the same externally observable defect against the C code shape rather than mechanically copying a path-specific patch.

Acceptance tests should target public behavior wherever possible so the same test semantics survive treatment C.

## T01 — Wake reconnect must ignore disposed transports

### Kind

`bug`

### Fixture

The frozen baseline already contains this defect.

No setup mutation is required for A/B.

Precondition:

```text
WebSocketService.isDisposed == true
connectionState == disconnected
document becomes visible
wasEverAuthed == true
```

Observed defect:

```text
visibility handler calls connect()
connect() rejects "WebSocketService disposed"
```

### Expected semantic owner

```text
capability://terminal/session/visibility-wake
```

Secondary contract:

```text
capability://web/transport/reconnect
```

### Acceptance

- disposed service: `connect()` is never called;
- live disconnected service: exactly one connect attempt;
- existing unauthenticated/non-disconnected guards remain intact.

## T02 — Late attach success after route switch must be ignored

### Kind

`bug`

### Why a fixture is required

The frozen baseline already guards late attach resolution with an attach-generation epoch.

### A/B fixture mutation

Introduce a narrow defect in the fulfilled-result path:

```text
late result from a superseded attach:
  if result.ok:
    allow it to dispatch ATTACH_OK
  else:
    keep stale-failure guard
```

The mutation must preserve normal current-generation attach success.

One acceptable implementation-level mutation is to make stale-success bypass the existing `gen !== attachGeneration` early return while stale failures remain ignored.

### Observable defect

1. Start attach on transport/route generation N.
2. Supersede/cancel it by changing route.
3. Start generation N+1.
4. Resolve N with `{ ok: true }`.
5. Old success incorrectly marks current attach state as attached.

### Expected semantic owner

```text
capability://terminal/session/reattach
```

Secondary:

```text
capability://terminal/session/route-recovery
```

### Acceptance

A late success from N is a no-op after N has been superseded. Only the current attach attempt may produce ATTACH_OK.

## T03 — Late attach failure after cancellation must be ignored

### Kind

`bug`

### Why a fixture is required

The frozen baseline already ignores stale fulfilled failures and stale promise rejections.

### A/B fixture mutation

Preserve stale-success suppression but allow a stale failure/rejection to drive recovery.

The fixture should make at least these stale outcomes unsafe:

```text
{ ok: false, error: "timeout" }
promise rejection
```

### Observable defect

1. Start attach N.
2. Cancel/supersede N.
3. Resolve/reject N after cancellation.
4. reconnectCount increments, retry is requested, failure state changes, or relay fallback is triggered.

### Expected semantic owner

```text
capability://terminal/session/reattach
```

### Acceptance

All stale failure forms are no-ops and cannot mutate reconnect budget, phase, candidate routing, or relay fallback.

## T04 — Repeated transport-loss notification must be idempotent

### Kind

`bug`

### Why a fixture is required

The baseline has both phase guards and a disconnect re-entrancy guard.

### A/B fixture mutation

Remove the attached-phase eligibility guard for recoverable connection-state loss notifications while preserving the rest of connection handling.

Conceptually mutate:

```text
if next in {reconnecting, connecting}
   and phase == attached
```

into:

```text
if next in {reconnecting, connecting}
```

### Observable defect

Repeated state notifications for the same loss cycle repeatedly dispatch `TRANSPORT_LOST` and repeatedly emit recovery/route events.

### Expected semantic owners

```text
capability://terminal/session/route-recovery
capability://terminal/session/attach-state
```

### Acceptance

For one physical loss cycle / transport generation:

- at most one loss transition;
- at most one corresponding recovery event;
- no duplicate recovery work.

## T05 — Handshake refusal must not consume reconnect loops

### Kind

`bug`

### Why a fixture is required

The baseline intentionally distinguishes refusal from socket loss.

### A/B fixture mutation

In the live-socket handshake rejection path, route refusal through normal socket-loss recovery instead of definitive failure.

Conceptually:

```text
handshake rejection:
  failConnection()
```

becomes:

```text
handshake rejection:
  handleSocketLoss()
```

The fixture must still reject the original `connect()` promise.

### Observable defect

An explicit peer refusal increments reconnect attempt count, enters `reconnecting`, and schedules retries.

### Expected semantic owner

```text
capability://web/transport/reconnect
```

### Acceptance

A live explicit handshake refusal:

- rejects the connection attempt;
- settles in `disconnected`;
- leaves reconnect attempt budget unchanged;
- schedules no reconnect timer.

A true socket loss must still reconnect normally.

## T06 — Stale socket callbacks must not mutate the live connection

### Kind

`bug`

### Why a fixture is required

The baseline has physical-socket generation guards.

### A/B fixture mutation

Create one controlled stale-callback hole while keeping the rest of generation handling intact.

Preferred fixture:

- remove/bypass the generation guard from the asynchronous handshake-success continuation;
- keep current-socket normal handshake success unchanged.

Alternative fixture, if test ergonomics are better:

- remove the generation guard from `onclose` only.

Use one variant consistently for A/B.

### Observable defect

1. Physical socket N begins connecting/handshaking.
2. N is superseded by socket N+1.
3. N+1 becomes the current live transport.
4. A late callback from N changes connection state, resets reconnect budget, closes/supersedes current state, or schedules recovery.

### Expected semantic owner

```text
capability://web/transport/reconnect
```

### Acceptance

All stale callbacks from N are inert after generation N+1 is current.

# Hidden acceptance strategy

Formal coding branches should not contain benchmark-specific acceptance tests.

The isolated research CI base should contain hidden behavioral tests and select the appropriate one from the PR/task identity.

Conceptually:

```text
agent task branch
        +
research CI base
  hidden acceptance
        ↓
PR merge commit
        ↓
task-specific hidden test
+ normal repository tests/build/lint
```

This keeps the final oracle outside the agent's task branch while preserving normal repository feedback.

Visible existing tests remain available because they are part of the treatment environment.

# Fixture validation gate

Before a fixture is admitted:

1. apply the fixture to the treatment base;
2. run the hidden acceptance test and confirm it fails for the intended reason;
3. run unrelated smoke tests and confirm the fixture did not broadly break the repository;
4. record fixture commit SHA;
5. only then start coding-agent runs.

A fixture whose hidden test already passes is invalid.
