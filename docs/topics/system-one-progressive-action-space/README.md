# System One Progressive Action Spaces

> Status: Active research topic.

## Purpose

This topic studies how a fast System One judgment model can participate in an agent runtime without being asked to generate arbitrary plans, tool calls, commands, or text.

The working thesis is:

> The environment may have an enormous or effectively unbounded global state space. System One only needs a small, grounded local view and a finite action frontier at each decision point.

The runtime is responsible for progressively discovering the world, accumulating observations into state, deriving currently valid affordances, and turning those affordances into typed action candidates.

System One is responsible for judgment at the ambiguous branch.

## 1. The key shift

A naive design starts with a finite-state-machine assumption:

~~~text
all states are known
+
all transitions are known
~~~

That does not fit Kubernetes, code repositories, browsers, cloud infrastructure, or most real agent environments.

A more useful model is:

~~~text
global environment
  -> large / dynamic / not fully enumerable

current knowledge state
  -> finite because it contains only observed facts

current action frontier
  -> finite because it is compiled from the current knowledge state
~~~

The runtime therefore does not require a finite world.

It requires a finite local frontier.

## 2. Progressive state disclosure

The environment is observed incrementally.

~~~text
Observe
  |
  v
Extract facts and entities
  |
  v
Update knowledge state
  |
  v
Derive affordances
  |
  v
Compile local action frontier
  |
  v
Choose / execute
  |
  v
Observe again
~~~

An action can reveal information that was not available when the previous action was selected.

Therefore the action space is itself state-dependent:

~~~text
A_t = Frontier(S_t, Goal, Policy)
~~~

A decision can be expressed as:

~~~text
a_t = Decide(S_t, A_t, Goal)
~~~

Execution creates a new observation and therefore a new state:

~~~text
S_(t+1) = Reduce(S_t, Observe(Execute(a_t)))
~~~

The next action frontier can now be different:

~~~text
A_(t+1) = Frontier(S_(t+1), Goal, Policy)
~~~

This is a lazily expanded state/action graph rather than a globally enumerated FSM.

## 3. Finite action templates, dynamic action instances

A critical distinction is between the action ontology and the current action instances.

Kubernetes can have a finite set of action templates:

~~~text
discover_namespaces()
select_namespace(namespace)
discover_pods(namespace)
emit_logs_command(namespace, pod, container?)
~~~

But the parameterized instances are discovered at runtime:

~~~text
select_namespace("staging")

emit_logs_command(
  namespace="staging",
  pod="nession-staging-7d4c6d9d7f-k8m2p"
)
~~~

The namespace and pod names are not generated by the model. They exist because an observation introduced typed entities into the current knowledge state.

This gives the runtime a clean rule:

> Models may select grounded actions; the environment and runtime own resource identity.

## 4. Kubernetes walkthrough

Consider the request:

> Show me the Kubernetes logs for nession in staging.

At the beginning, the runtime does not need to know every namespace, workload, pod, container, log stream, or Kubernetes object.

### Step 1: discover namespaces

The initial frontier can contain only:

~~~text
discover_namespaces
~~~

Because there is a single valid action, no model call is necessary.

The environment executes a read-only observation equivalent to:

~~~text
kubectl get namespaces -o json
~~~

Suppose the observation reveals:

~~~text
default
kube-system
monitoring
staging
~~~

The knowledge state expands.

### Step 2: compile namespace choices

The runtime can now instantiate:

~~~text
namespace:default
namespace:kube-system
namespace:monitoring
namespace:staging
~~~

This is the first semantic branch.

System One receives the goal, current state, and only those grounded candidates. It selects:

~~~text
namespace:staging
~~~

### Step 3: discover pods

The selected namespace unlocks another deterministic observation:

~~~text
kubectl -n staging get pods -o json
~~~

Suppose that reveals:

~~~text
nession-staging-7d4c6d9d7f-k8m2p
postgres-staging-0
redis-staging-0
~~~

The state expands again.

### Step 4: compile log-target choices

The runtime builds a new local frontier from the observed pod/container entities.

System One can choose the nession pod.

### Step 5: deterministic lowering

The runtime validates that the selected namespace, pod, and optional container still refer to grounded state and renders:

~~~text
kubectl -n staging logs nession-staging-7d4c6d9d7f-k8m2p
~~~

The command was assembled from typed state. It was not generated as free-form model output.

## 5. Mapping to the TypeSafe System One API

TypeSafe System One provides a useful primitive for the decision step because a request evaluates a state against typed questions.

The demo maps the runtime to the API as:

~~~text
state
  = goal
  + current phase
  + discovered Kubernetes entities
  + selected entities
  + policy metadata
  + recent decisions

questions.next_action
  type = choice
  criteria = current grounded action frontier

model
  = jev-latest
~~~

The Choice result gives the runtime an action identifier plus probability/confidence information.

That means the model is not responsible for:

- generating kubectl syntax;
- inventing namespace names;
- inventing pod names;
- inventing container names;
- deciding whether a shell string is safe;
- mutating the durable state directly.

It supplies judgment over a frontier prepared by the harness.

## 6. The runtime should skip trivial judgment

System One is useful at ambiguous semantic branches, not as ceremony around deterministic transitions.

The runtime should therefore distinguish:

~~~text
0 candidates
  -> blocked, discover more, or escalate

1 candidate
  -> execute deterministically

N candidates
  -> ask System One to choose
~~~

This reduces latency, model traffic, and opportunities for unnecessary judgment.

## 7. Affordance compilation

The hardest harness problem is not the Choice API. It is the transition from observation to available actions.

The working answer is an affordance compiler.

~~~text
Observation
  -> typed entities
  -> entity capabilities
  -> policy filtering
  -> parameter binding
  -> local action instances
~~~

For Kubernetes, a typed entity can unlock a known set of affordances.

~~~text
Namespace
  -> discover workloads
  -> discover pods
  -> discover events

Pod
  -> inspect
  -> logs
  -> events

Container
  -> logs
~~~

The model does not infer these capabilities from raw command help on every step. The harness owns the action ontology.

What changes dynamically is which action instances can be bound safely from the current observations.

## 8. Command generation is lowering, not generation

A useful compiler analogy is:

~~~text
user intent
  |
  v
runtime state
  |
  v
typed grounded action
  |
  v
validated action IR
  |
  v
deterministic lowering
  |
  v
argv
~~~

For example:

~~~text
LogsAction {
  namespace: "staging",
  pod: "nession-staging-7d4c6d9d7f-k8m2p",
  container: null
}
~~~

lowers to:

~~~text
["kubectl", "-n", "staging", "logs", "nession-staging-7d4c6d9d7f-k8m2p"]
~~~

This is safer and easier to validate than asking a model to emit a command string.

The same idea can generalize to code-navigation operations, browser actions, database exploration, cloud APIs, and other tool ecosystems.

## 9. Local frontier size

A dynamic world can still produce too many candidates.

TypeSafe Choice is bounded, so large environments need hierarchical or deterministic narrowing instead of blindly sending the entire world to the model.

For Kubernetes:

~~~text
cluster
  -> namespace
  -> resource class
  -> workload
  -> pod
  -> container
  -> operation
~~~

The ordering does not have to be fixed forever. The important property is that each model-mediated branch remains bounded and grounded.

The demo conservatively blocks above 200 local candidates rather than silently truncating them.

A future experiment should compare:

- deterministic hierarchy;
- semantic prefiltering;
- search-based retrieval;
- multiple independent Choice questions;
- System Two planning for frontier restructuring.

## 10. Freshness is part of state validity

Progressive discovery creates another runtime concern: observed entities can disappear or change.

A production design should treat observations as versioned or time-bounded facts.

Before an externally meaningful action, the runtime may need to:

~~~text
selected grounded action
  -> freshness check
  -> policy check
  -> execute
~~~

If the state is stale, the correct transition may be to observe again rather than execute.

This is especially important for Kubernetes because pods are routinely replaced and generated names are ephemeral.

## 11. Durable state-machine direction

The in-repository demo is intentionally in-memory, but the same control model fits a durable runtime.

A durable state could include:

~~~text
goal

knowledge
  observations
  entities
  provenance
  freshness

frontier
  available actions
  action parameters

tasks
  running
  waiting
  completed

decisions
  selected action
  model probabilities
  confidence

policy
  permissions
  budgets
  approvals

events
  observations
  decisions
  executions
  failures
~~~

A durable implementation should persist enough information to replay why an action was available and why it was selected.

That suggests an event flow such as:

~~~text
ObservationRecorded
  -> StateReduced
  -> FrontierCompiled
  -> JudgmentRequested
  -> ActionSelected
  -> ActionValidated
  -> ActionExecuted
  -> ObservationRecorded
~~~

The precise transaction and replay semantics remain future research.

## 12. System One and System Two boundary

This model gives the two classes of model different responsibilities.

System One is suitable for:

- choosing among grounded local actions;
- ranking observed candidates;
- deciding between a small number of semantically meaningful branches;
- scoring urgency, relevance, or likely fit;
- fast repeated judgments over a changing local state.

System Two becomes useful when:

- the action ontology does not contain a useful next step;
- the goal needs reinterpretation;
- repeated local decisions make no progress;
- the runtime needs a new capability or tool family;
- a large frontier cannot be narrowed by existing rules;
- a high-risk decision requires deeper reasoning.

A useful framing is:

~~~text
System One:
  Which branch in the currently known local world?

System Two:
  Are we exploring the right world, with the right representation and capabilities?
~~~

## 13. Safety and authority

Confidence is not authorization.

Even a high-confidence System One decision should remain subject to deterministic controls.

A production path should look closer to:

~~~text
System One judgment
  -> grounded-action validation
  -> freshness validation
  -> RBAC / capability policy
  -> approval policy
  -> deterministic execution
  -> evidence / observation
~~~

Mutating Kubernetes commands should require stronger policy than the read-only discovery demonstrated here.

## 14. Generalized runtime boundary

The Kubernetes prototype suggests a reusable interface:

~~~text
Environment.observe(...)
Reducer.apply(...)
Frontier.compile(...)
Decider.choose(...)
Validator.check(...)
Executor.execute(...)
~~~

The environment adapter owns domain-specific facts and read operations.

The reducer owns durable or in-memory knowledge.

The frontier compiler owns the mapping from known entities to currently legal action instances.

The decider can be System One, System Two, a deterministic rule, a human, or another policy.

The validator and executor remain outside the model.

This separation is more important than any particular kubectl command.

## 15. Research hypotheses

The Kubernetes demo exists to test several hypotheses.

### H1: Local finiteness is enough

A globally large environment can be navigated if each step exposes a bounded grounded frontier.

### H2: State expansion can replace free-form planning for some tasks

For bounded operational goals, repeated observe -> compile -> choose cycles may be sufficient without a long natural-language plan.

### H3: Typed selection is safer than text generation

Selecting grounded IDs and deterministically lowering them should reduce hallucinated resources and malformed commands.

### H4: Deterministic short-circuiting matters

Skipping the model when there is only one legal action should improve latency and trace clarity.

### H5: Environment adapters are the real harness leverage point

The quality of entity extraction and affordance compilation may matter more than prompt sophistication.

## 16. Measurements and hosted experiment evidence

A useful comparison against a System Two command-generating agent can measure:

- total model calls;
- latency;
- tokens or request size;
- invalid resource references;
- malformed commands;
- number of discovery steps;
- command correctness;
- stale-state failures;
- escalation rate;
- ability to recover after a pod is replaced;
- trace explainability.

The repository now hosts the Kubernetes prototype through GitHub Actions. Each run emits an append-only JSONL trace plus a final state snapshot and derived analysis report.

The trace records:

~~~text
runtime_started
frontier_compiled
action_selected
observation_recorded
state_bound
model_exchange
command_rendered
runtime_completed / runtime_blocked
~~~

This makes the research falsifiable at the harness level. A run can be inspected for the exact frontier visible at each decision, which steps were deterministic, which steps were model-mediated, and how each observation expanded the next local action space.

Real TypeSafe runs also preserve the structured API request and response, including probabilities, confidence, model version, usage, and latency. The authorization secret is deliberately excluded.

The first hosted offline fixture run produced this path:

~~~text
frontier sizes: 1 -> 4 -> 1 -> 4
decisions: 4
deterministic short-circuits: 2
observations: 2

discover.namespaces
  -> namespace:staging
  -> discover.pods:staging
  -> logs:nession-staging-7d4c6d9d7f-k8m2p

final:
kubectl -n staging logs nession-staging-7d4c6d9d7f-k8m2p
~~~

The offline run is a control for the runtime and frontier mechanics, not evidence about Jev quality. A real TypeSafe run is needed to evaluate the System One judgment steps.

The result should distinguish between tasks that are naturally frontier-driven and tasks that require open-ended reasoning.

## 17. Open questions

- What is the right Kubernetes entity/affordance ontology?
- How should a large namespace or pod set be narrowed?
- When should discovery itself be chosen by System One rather than predetermined?
- How should observation freshness be represented?
- Should action frontiers be persisted or always recomputed from state?
- How should probability/confidence affect retry or escalation without becoming authorization?
- What is the right durable event model?
- How should a System Two planner add or reconfigure capabilities?
- Can the same runtime interface serve Kubernetes, coding, and browser environments?
- How much state should be sent to System One at each branch?

## 18. Code localization experiment

The second reference experiment applies the same progressive-disclosure idea to source-code localization.

```text
repository
  -> directory candidates
  -> relevant directories
  -> file candidates
  -> relevant files
  -> source-line candidates
  -> grounded code snippets
```

Unlike Kubernetes action selection, this stage is not a single-winner decision. Multiple directories, files, and source ranges can all be relevant, so the prototype uses independent Noul judgments rather than Choice.

The harness owns traversal, filesystem IO, batching, thresholds, provenance, and range merging. System One only estimates candidate relevance.

This broadens the working runtime abstraction:

```text
StateSpaceGenerator
  -> CandidateSet
  -> DecisionPrimitive
  -> TransitionPolicy
  -> EvidenceRecorder
```

The decision primitive can therefore vary by state:

- `Choice` for selecting one grounded action from a local frontier;
- `Noul` for independently retaining multiple relevant candidates;
- deterministic short-circuiting where model judgment is unnecessary.

See [Hierarchical Code Localization with System One](../../../research/code-locator/docs/design.md) for the hypotheses, threshold/recall analysis, evidence contract, and experiment plan.

## 19. Research evidence workflows

The experiments use separate workflows because they exercise different decision primitives, inputs, costs, and failure modes.

- [System One Kubernetes experiment](../../../.github/workflows/system-one-k8s-experiment.yml) owns only the Kubernetes state-machine demo.
- [System One Code Locator experiment](../../../.github/workflows/system-one-code-locator.yml) owns only hierarchical code localization.

The Code Locator workflow has two layers:

1. deterministic fixture validation on Code Locator changes, requiring no external model service;
2. manually dispatched real-System-One localization against a configurable subject repository.

Its artifact contains only Code Locator evidence: run metadata, execution log, `trace.jsonl`, `result.json`, and `summary.md`. This keeps repository-localization research independent from Kubernetes results and makes failures, costs, and parameter sweeps attributable to one experiment.

## 20. Relationship to Narness

Narness currently defines itself as AI Workspace Engineering and explicitly does not aim to become a general Agent Runtime.

This topic therefore remains research rather than a canonical Narness runtime commitment.

It is still relevant because it explores a neighboring harness-engineering question:

> How should an execution environment expose context, capabilities, constraints, and deterministic actions so that a model only needs to make the smallest useful judgment?

If the conclusions stabilize, some of them may graduate into Narness concepts around progressive disclosure, capability representation, deterministic execution, policy, evidence, and agent observability without requiring Narness itself to own a runtime.
